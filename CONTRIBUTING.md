# Contributing to @cosborn2/ui

Use pull requests for changes. Describe the user-visible result, compatibility impact, and validation. Discuss large API or dependency changes in an issue first. Report vulnerabilities privately using [SECURITY.md](SECURITY.md).

## Local setup

Use Node.js 26 and the Bun version in `.bun-version` (also declared in `package.json`). From the repository root:

```sh
bun install --frozen-lockfile
bun run lint
bun run test
bunx playwright install chromium
bun run test:browser
```

`lint` includes type checking. `test:browser` builds and packs the library, runs package checks, and verifies isolated plain React and production Next consumers. Use `bun run test:package` for the non-browser subset; there is no need to run it separately when running the full browser suite. See the [fixture guide](fixtures/README.md) for focused runs and retained artifacts. `bun run dev` watches library source and styles during development.

## Component changes

- Preserve granular JavaScript and CSS entry points. A small consumer must not inherit unrelated component, icon, or dialog code.
- Keep static components server-compatible. Add client boundaries only where interaction requires them, and verify server HTML agrees with initial hydration.
- Support React applications without Tailwind. Import only the icons a component needs, and preserve scoped theme behavior.
- Test meaningful behavior changes, including keyboard navigation, focus restoration, nested dialogs/menus, and accessible names where relevant.
- Review the packed fixture's compressed size and dependency graph results. Investigate budget failures rather than widening limits automatically. Explain any necessary increase in the PR.

Edit `tokens.json` for canonical theme changes; the build generates the packaged theme. Do not add application-specific services or styling dependencies. Lucide is pinned for verified Server Component behavior; upgrades require the SSR and size checks.

## Review and release

The `verify` check must pass before a PR can merge. Contributions require the maintainer's approval. While there is one maintainer, the owner's own PRs use an explicit review exception; CI remains mandatory. Merges are squash-only. See [repository settings](docs/repository-settings.md) for the intended protections.

Versions are chosen in reviewed release PRs, not generated by CI. Update the `package.json` version when a change should ship, run `bun install` to refresh the lockfile, and commit any resulting `bun.lock` changes. A version-only bump may leave the lockfile unchanged. During the initial beta, increment `0.1.0-beta.N`; the first stable version will be `0.1.0`. Compatible fixes use patch versions and new APIs use minor versions. Before `1.0`, breaking changes require a new minor version and migration notes. Documentation-only maintenance does not require a package release.

Publishing is a maintainer task. Follow the [publishing runbook](docs/publishing.md); do not add npm credentials to the repository or PR. The automatic publishing gate remains disabled until the initial npm publication and trusted publisher setup are complete.
